# Bubble 剧情 / 事件 AI 配置工作流

> 版本：2.0  
> 更新日期：2026-09-03  
> 适用范围：剧情、独立对白、事件、事件内对白、事件完成后剧情，以及它们与新手引导之间的信号连接。

## 1. 工作流解决什么问题

团队只维护一份长期活动需求池。策划写玩家要经历什么，AI 负责根据当前需求、正式配置表、运行时代码、Prefab 和关联数据形成可审查配置草案，并保留证据、假设、QA 和激活边界。

```text
活动需求池中的待配置需求
→ 锁定为配置中
→ 读取当前规则、源表、代码、Prefab 和关联表
→ 判断剧情 / 对白 / 事件 / 事件后剧情路线
→ 建立 S/T/D/A 证据与 ID 台账
→ 复制正式工作簿到本次输出目录
→ 在输出副本的合适位置写草案（不强制 END 下方）
→ 回读、静态、逻辑、引用和视觉 QA
→ 回填需求池与配置记录
→ 策划明确授权后才激活、导表和实机验证
```

“已完成”表示草案和约定 QA 已完成，不表示配置已进入正式区，也不表示客户端已经生效。

## 2. 团队文件

| 文件或目录 | 用途 |
|---|---|
| `剧情事件需求池.xlsx` | 唯一长期活动需求池；日常接单入口 |
| `剧情事件AI配置工作流.md` | 从接单到激活的完整流程 |
| `剧情配置说明_给AI使用.md` | 剧情、步骤、对白、角色与语言规则 |
| `事件配置说明_给AI使用.md` | 事件触发、池、组、详情与完成链规则 |
| `剧情事件AI输入模板/` | 旧版兼容资料；不再作为日常入口 |
| `AI生成/<功能_日期>/` | 每次生成的工作簿副本、清单、预览和 QA |
| `AI生成/配置记录/YYYY-MM.xlsx` | 已完成需求的月度归档与配置记录 |

正式配置源 `策划/配置表/Table` 始终只读。任何生成或修改都先发生在本次输出目录的完整工作簿副本中。

## 3. 角色与职责

| 角色 | 主要职责 |
|---|---|
| 需求提交人 | 在需求池写清玩家体验和已知限制；不需要填写内部 ID |
| AI 执行者 | 锁定需求、取证、分配 ID、在输出副本生成草案、做 QA、回填结果 |
| 策划审核人 | 确认触发、流程、对白、奖励、假设和待确认项；决定是否激活 |
| 客户端 / 测试 | 核对代码事件、Prefab 路径、导表结果、存档、中断和实机表现 |

## 4. 日常使用

1. 打开 `剧情事件需求池.xlsx` 的 `填写需求` 页，在下一空行填写“需求一句话”。
2. “内容性质、触发时机、玩家动作、对象与场景、特殊要求”均可选填；知道多少填多少。
3. 对 AI 说：`处理剧情事件需求池。`
4. 默认只处理“状态=待配置”且“需求一句话非空”的行，并按序号升序执行。
5. 只处理某行或某功能时，在指令中写明行号或功能名。
6. AI 完成后，先看 `AI假设与待确认`，再看配置记录、`generation-manifest.json`、目标 Sheet 预览和 QA 结果。

也可以直接说：

```text
用 $bubble-story-event-guide-config 配置：二楼修复后贵妇鹅出现，玩家点击后对话，结束后播放一段剧情。缺失值先做 A-假设草案。
```

直接提交的需求仍执行本文件规定的同一套证据、草案、QA 和激活流程。

## 5. 固定执行阶段

### 阶段 A：筛选与状态锁

- 只读 `填写需求` 页；不从示例、旧模板、归档和历史输出接单。
- 开始处理一条需求前，先把状态改为“配置中”，防止多人重复处理。
- 文件被占用、需求取消或无法安全继续时，状态恢复为“待配置”，并在“AI假设与待确认”中写明阻塞原因。

### 阶段 B：证据与分类

每个关键值必须记录来源：

- `S`：用户或正式策划需求明确给出。
- `T`：当前表、代码、Prefab、枚举或关联数据直接证明。
- `D`：由 S/T 可复核推导。
- `A`：为形成审查草案而补充的假设。

根据需求选择主路线：

| 需求信号 | 主路线 |
|---|---|
| 过场、自动对白、Timeline、奖励、发任务 | `tPlot → tPlotStep → 对话/Timeline/奖励/任务` |
| 只改一组对白 | `tDialogueTable → tDialogContent → tGuideTrole/tlanguage_cn`，并反查消费者 |
| 角色或对象出现并点击/靠近说话 | 事件详情 + 核心事件链 + 对话链 |
| 矿下 NPC、团餐、流行菜、特殊顾客、商人 | `Trigger → Pool → Group → 同 ID 详情表` |
| 事件完成后播放正式剧情 | 先闭合事件，再由 `tPlot` 监听具体事件 ID |
| 引导完成后启动事件或剧情 | 先确认信号生产者，再配置消费者 |

高风险 ID、枚举、资源路径、触发、存档和中断行为缺少 T 证据时，只能标为 `A-假设`，不得写成已验证事实。

### 阶段 C：ID 与引用计划

先建立候选 ID 台账并做作用域内冲突检查，再写入工作簿。禁止使用全局 `MAX+1`，禁止混用以下四类事件 ID：

```text
tEventTrigger.eventPoolId[] 元素 = tEventPool.eventType
tEventPool.eventTypeId[] 元素     = tEventGroup.groupId
tEventGroup.id                    = 对应事件详情表.id
tPlot 的事件条件参数              = 具体 tEventGroup.id
```

剧情、步骤、对白组、单句和语言 ID 要保持当前模块的业务号段、父子前缀和句序习惯。玩家可见文字写入 `tlanguage_cn`，业务表只引用语言 ID。

### 阶段 D：工作簿副本与草案写入

- 从 `策划/配置表/Table` 复制所需完整工作簿到 `AI生成/<功能_日期>/`。
- 保留 6 行协议头、Sheet 名、字段拼写、样式、公式、图片、隐藏状态和数据验证。
- 草案位置按目标表 schema 和输出副本结构决定，不强制放在 `END` 下方。若存在 `END` 导出截止标记，在副本中保留其位置和语义。
- 修改既有正式行时，只在输出副本中保留原值、写入变更记录并生成草案，不直接改正式区或正式文件。
- 数组和复合参数必须使用当前字段要求的严格 JSON。

推荐按依赖拓扑生成：

1. 语言、角色、条件、奖励等叶子数据。
2. 对话单句与对白组。
3. 事件详情和具体 `tEventGroup.id`。
4. Event Group、Pool、Trigger。
5. 剧情步骤与剧情入口。
6. 反向验证生产者确实能完成，消费者确实监听正确 ID。

### 阶段 E：QA 与交付

保存后必须重新打开最终工作簿，至少完成：

- 结构 QA：副本工作簿、Sheet、协议头、草案位置和（如存在）END/导出语义正确。
- 数据 QA：必填、类型、严格 JSON、公式缓存和错误值正确。
- 引用 QA：ID 唯一，外键存在，语言正文非空，数组长度一致。
- 剧情 QA：入口、步骤顺序、对白、角色、Timeline、奖励和场景链闭合。
- 事件 QA：Trigger/Pool/Group/详情可达，区间不误遮挡，完成通知和后续消费者正确。
- 视觉 QA：渲染受影响 Sheet，检查表头、草案位置、长文本、颜色和裁切。

每条成功需求至少交付：工作簿副本、`generation-manifest.json`、配置记录、预览或渲染证据、QA 结果、测试步骤和成熟度。

成熟度只能使用符合证据的状态：

- 草案已生成，静态 QA 通过，尚未导出。
- 已激活并导表，等待实机验证。
- 实机验证通过。
- 阻塞，等待指定确认或外部条件。

### 阶段 F：需求池回填

成功后把状态写为“已完成”，并回填：

- AI 配置判断
- 涉及配置表
- 使用 / 新增 ID
- 输出文件位置
- AI 假设与待确认
- 完成时间

没有实机证据时，不得把成熟度写成“正式生效”或“实机通过”。

## 6. 激活正式区

只有策划明确说“激活”“写入正式区”或同义授权后，才可把确认过的草案交给人工/项目发布流程处理。AI 不直接合并正式区、不覆盖正式文件、不执行正式导表；发布后由负责人重新完成全量 QA、导表和实机测试，并记录激活时间、版本和结果。

同一个 ID 在副本草案中必须标明与正式行的关系，不能误称为已生效。任何人工激活前都要保留可恢复副本并重新做冲突检查。

## 7. 归档与版本维护

- 活动池中“已完成”记录达到 50 条时，先追加到 `AI生成/配置记录/YYYY-MM.xlsx`。
- 归档文件回读校验成功后，才从活动池移出旧完成记录；保留最近完成记录便于协作。
- 历史记录不是经验库。可复用规则应更新到本工作流、剧情/事件配置说明或需求池的 `AI配置规则` 页。
- 规则源、表结构或代码行为变化时，更新 skill 内快照并运行漂移检查和 skill 校验。

## 8. 审核顺序

```text
需求池 AI假设与待确认
→ 配置记录与 generation-manifest.json
→ 目标 Sheet 副本预览和草案位置
→ 策划确认
→ 明确授权激活
→ 导表
→ 客户端实机验证
```
